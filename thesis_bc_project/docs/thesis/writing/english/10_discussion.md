# Chapter 10 Discussion

This chapter integrates the results from Chapter 6 through Chapter 9 and interprets the relationships among performance, optimization factors, capacity, and numerical behavior. Chapter 11 consolidates the formal answers to the Research Questions. This chapter distinguishes observed facts from unverified inferences. It also avoids conflating results for the corrected 325557 graph with historical evidence from the former malformed input.

## 10.1 Interpretation of Performance Results

Chapter 6 showed that the fixed-`b512` block-based GPU_Opt had a shorter median runtime than tuned third-party PathMerge on each of the 4 evaluated graphs. However, the magnitude of the speedup was not uniform across graphs. Table 6.1 and Figures 6.1–6.2 present the primary performance values and statistics, so this chapter does not repeat them. This difference is an observation under the evaluated conditions, and no single optimization factor necessarily explains it.

The factorial ablation in Chapter 7 showed positive main effects for Hybrid BFS and Dual-Stream Execution. The direction and magnitude of the effect of Warp-Cooperative Accumulation varied by graph. However, the ablation graph set differs from that of the main RQ1 performance comparison, and the Synthetic-4 aggregate is mixed-checkpoint. Adding or multiplying the H/W/A main effects therefore cannot causally decompose the end-to-end speedup in Chapter 6.

In the forced comparison on roadNet-PA/TX, the block kernel had a shorter runtime than the shared kernel. This result supports the selection of the current block-based source assignment. However, the comparison covers only 2 graphs. The phase breakdown in Figure 7.3 and the kernel proportions from a single trace likewise report observed time distributions for the measured configurations, not contribution percentages for individual optimizations.

## 10.2 Graph Characteristics and Observed Behavior

As Table 5.3 shows, email-EuAll and the roadNet graphs differ in mean degree, degree distribution, BFS depth, and graph size. email-EuAll contains hubs and has relatively shallow traversals, whereas roadNet has low degrees and deep traversals. These structural differences are consistent with the speedup differences in Chapter 6. However, the number of evaluated graphs is small, and this study did not analyze causal relationships between graph characteristics and performance differences.

Dual-Stream Execution showed a large positive main effect on email-EuAll, suggesting that the overlap of initialization and kernel execution may have affected runtime. However, this study did not conduct the H/W/A factorial ablation on the roadNet graphs, so this interpretation does not apply to their speedups. Similarly, graph-wise differences in Warp-Cooperative Accumulation may relate to adjacency-scan volume or lane utilization. No dedicated hardware counters verified these possibilities, so mean degree alone does not provide a general predictive rule.

Graph size affects not only static CSR and BC-output sizes but also the batch-dependent working set through the state required for 1 source vertex. However, the capacity evaluation covers only 1 graph, the corrected 325557 graph. This study therefore does not extrapolate feasibility boundaries for other graphs from their vertex or edge counts alone.

## 10.3 Performance–Capacity–Numerical Trade-Off

The central distinction in the capacity evaluation in Chapter 8 is between static graph storage and batch-dependent source-local state. For the corrected 325557 graph, neither the input graph file nor the CSR topology itself exceeded HBM3 capacity. Instead, concurrently retained source-local state dominated the working set. Section 8.1.2 defines this relationship with the working-set equation, which this chapter does not repeat.

GPU_Opt, GPU_Opt_Pure, and GPU_Opt_Pure_Chunked are not 3 independent proposals. They are memory-management variants of a common framework that manage this working set differently. GPU_Opt uses managed placement through Unified Memory, whereas GPU_Opt_Pure explicitly places data in device memory. GPU_Opt_Pure_Chunked limits the concurrently resident state through source sub-batching. Batches and sub-batches divide the source set, not the graph, and they perform neither graph partitioning nor source sampling. All variants therefore retain the execution unit of exact BC that processes every source vertex.

The targeted boundaries in Chapter 8 showed that Unified Memory handled a larger batch than Pure, while Chunked further extended the tested upper bound. They did not establish a performance ranking among the variants. Each boundary condition had 1 trial, and the batch, allocation path, and number of sub-batches differed. Unified Memory depends on finite host memory and resource limits, and available evidence does not guarantee that Chunked avoids OOM under unmeasured conditions.

Numerically, Tier A in Chapter 9 evaluated full-vector consistency against an independent reference on small graphs. Tier B evaluated cross-implementation consistency across batches and memory paths on the corrected 325557 graph. A PASS within the mixed tolerance does not mean byte-identical results, and PathMerge remains an external comparator rather than an independent reference. Selecting an execution path that changes performance or capacity must therefore consider both feasibility and the meaning of its evidence tier and numerical decision.

## 10.4 Implications for GH200

In the evaluated GH200 configuration, the coherent memory architecture connects Hopper GPU HBM3 with Grace CPU-side memory. This architecture enabled comparison of device-only, Unified Memory, and source sub-batching paths within the same computational framework. The observed boundaries show that design must consider the amount of concurrently resident source-local state, not only graph-file size.

Unified Memory simplifies allocation and placement management but remains subject to host-memory pressure, resource limits, and migration. Source sub-batching provides explicit control over the resident working set but requires a sub-batch loop and additional launches. This study did not collect full-run process RSS, physical HBM residency, total host residency, or full-run migration bytes. It therefore does not quantitatively compare physical placement or infer the cause of migration costs between the two paths.

This study evaluated Hybrid BFS, Warp-Cooperative Accumulation, Dual-Stream Execution, and block-based source assignment only on GH200. These results do not support inference of the same performance relationships or capacity boundaries on GPUs with different stream concurrency, memory capacity, interconnects, or runtime policies.

## 10.5 Threats to Validity

**Internal validity.** The Synthetic-4 aggregate for RQ2 is mixed-checkpoint, not a same-checkpoint four-graph remeasurement. The targeted boundaries for RQ3 had 1 trial per condition, and separate measurement series produced the RQ2, RQ3, and RQ4 results. The primary comparisons are median-based, and small trial counts restrict the discussion to descriptive interpretation rather than broad inference. Warmup records also differ across current, legacy, and historical measurement series. This study distinguishes the CUDA device-memory OOM for Pure from the cgroup host-memory OOM kill for Unified Memory and does not treat failures as runtimes of 0 seconds. For the Unified Memory failure, the per-configuration runtime record contained a `none` classifier and a SIGKILL-compatible termination. The retained PBS epilogue independently recorded the cgroup OOM event.

**External validity.** RQ1 covers only 4 graphs, and RQ2 covers the 4 synthetic graphs and email-EuAll. RQ3 and RQ4 Tier B cover only the corrected 325557 graph, while Tier A covers 3 small graphs. The evaluation also used 1 GH200. This study does not generalize these results to unmeasured graphs, other GPUs, or different host-memory limits. The corrected 325557 graph is not part of the main RQ1 performance comparison.

**Construct validity.** The working-set values are code-derived allocation estimates based on array dimensions, not measured RSS, physical residency, or migration bytes. A correctness PASS indicates numerical consistency within the predefined mixed absolute-relative tolerance, not bitwise identity. This study does not treat observed runtime, main effect, phase proportion, and feasibility as the same performance measure.

**Baseline and data validity.** This study evaluated a snapshot of a third-party PathMerge implementation, not the original authors' official implementation or ground truth. Its upstream license was not independently verified, and this study does not extend the results to PathMerge in general. The corrected 325557 graph is deterministic internally reconstructed data, but its original seed and upstream original remain unconfirmed. The repair retained 87,442 self-loops and 866,924 duplicate ordered pairs with multiplicity 2. This representation has not received independent validation against simple-graph semantics. These values describe the retained adjacency representation; this study does not identify them as causes of performance differences. The `CORE_FAIL` for the former malformed input remains historical invalid-input evidence, and the current conclusion does not use it.

## 10.6 Limitations and Future Work

The principal current limitations are the absence of an independent full-vector reference for the 4 headline graphs and of a unified current 7-implementation comparison using the block-based implementation. The PathMerge comparison also uses only a single third-party implementation. The capacity evaluation covers 1 graph with 1 trial per condition and lacks full-duration measurements of RSS, HBM residency, host residency, and migration. Only partial profiling traces remain available, and some historical comparison vectors are unavailable. The evaluation includes neither multi-GPU execution nor other GPU models. The factor analysis retains a mixed-checkpoint aggregate, and the corrected 325557 graph has provenance limitations regarding the upstream original and generation seed.

Addressing these limitations first requires independent full-vector references for the headline graphs and large-scale conditions. Future work should also compare an official or independently developed PathMerge implementation with the current block-based implementation under the same conditions. It should then broaden the evaluation through a same-checkpoint Synthetic-4 ablation, additional graphs, multiple trials at capacity boundaries, and evaluations on other GPUs. Finally, full-run memory telemetry and confirmation of the upstream original or generation seed would allow separate examination of the current performance, capacity, numerical-behavior, and provenance constraints.

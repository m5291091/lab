# Chapter 3 Related Work

This chapter reviews research on exact Betweenness Centrality (BC) computation, GPU-based BC computation, direction-optimizing BFS, the evaluated GPU baselines, and processing beyond memory capacity. Chapter 2 presented the BC definition and computational steps of the Brandes algorithm. This chapter does not repeat that material. Instead, it focuses on the development of parallelization and memory management. Finally, it clarifies how this study integrates established components and what it evaluates.

## 3.1 Exact Betweenness Centrality

The Brandes algorithm combines a shortest-path search from each source vertex with reverse dependency accumulation, without separately enumerating shortest paths for every vertex pair. For an unweighted graph, processing 1 source requires BFS and edge scans. The general all-sources time complexity is therefore $O(|V|(|V|+|E|))$, and the auxiliary space complexity is $O(|V|+|E|)$ [@brandes2001]. Only when $|E|=\Omega(|V|)$ can the time complexity be simplified to $O(|V||E|)$. This approach greatly increased the practicality of exact BC compared with direct all-pairs processing. Chapter 2 presented the equations and dependency recurrence. This section therefore focuses on how source-by-source processing provides a unit of parallelization.

The contribution of one source can be computed without referring to the traversal state of another source. Multiple sources can therefore be assigned to CPU threads, GPUs, or distributed computing resources. Their partial BC values are then summed vertex by vertex, enabling source-level parallelism. Each worker, however, needs source-local state such as distance, shortest-path counts, dependencies, and frontiers. Increasing the number of sources increases parallelism, but the workspace may grow in proportion to the number processed concurrently.

Sarıyüce et al. use this coarse-grained parallelism in a CPU implementation. For each source, 1 thread handles the contribution and maintains thread-local arrays for traversal and accumulation, reducing synchronization among sources. Their evaluation includes multiple threads on a multi-core CPU. The GPU portion of the same study parallelizes computation within each source at a finer granularity [@sariyuce2013]. This design shows that source independence is convenient for multi-core parallelization, although per-thread state and a final reduction remain necessary.

The same decomposition can be applied to distributed-memory processing. The source set can be divided among ranks or nodes, each resource can produce a partial BC vector, and the vectors can then be summed. For example, McLaughlin and Bader distribute subsets of roots across a multi-node, multi-GPU environment and combine the results for exact BC computation [@mclaughlin2014]. Source-level parallelism provides outer parallelism with little communication in this design. Graph-replication capacity, partial-vector reduction, and load differences among sources remain design constraints for distributed execution.

The two forms of parallelization, across sources and within a source, are not mutually exclusive. The former is coarse-grained parallelism that executes independent traversals concurrently. The latter is fine-grained parallelism that distributes 1 source's frontier or edges among multiple workers. The two forms can be combined hierarchically according to CPU thread count, GPU execution width, frontier width, and available memory.

Exact BC must be distinguished from approximate BC. Exact all-sources BC processes contributions from every source vertex. In contrast, approximation based on source sampling estimates the whole from selected sources, introducing a trade-off between computational cost and error. For example, the official cuGraph API distinguishes exact computation over all sources from approximation using seed sources [@rapidsCugraphBcDocs]. Approximate BC is an important direction for scaling, but it is not a direct comparison target in this study. This study targets exact all-sources BC on undirected, unweighted graphs and omits no source vertex.

## 3.2 GPU-Based BC Computation

GPU-based BC computation must map each source's BFS and dependency accumulation to SIMT execution while also exploiting the Brandes algorithm's parallelism across sources. Major design dimensions include concurrent source count, frontier representation, thread assignment to vertices or edges, conflicting shortest-path-count updates, and placement of source-local state. Frontier sizes and vertex degrees change across processing stages. Graph processing therefore presents load-balancing problems unlike those of regular dense computation.

Sarıyüce et al. investigate heterogeneous BC that combines coarse-grained CPU parallelism with fine-grained GPU parallelism. On the GPU, they compare a vertex-based approach, which assigns threads to frontier vertices, with an edge-based approach, which assigns threads to outgoing frontier edges. The vertex-based approach scans adjacency edges from each frontier vertex. A thread assigned to a high-degree vertex runs longer, making skewed degree distributions prone to load imbalance. The edge-based approach can more readily expose edge-level parallelism and aligned memory access, but it requires edge-frontier management and additional atomic operations [@sariyuce2013].

The shortest-path count $\sigma$ is subject to conflicts when contributions from multiple predecessors at the same level reach one vertex. Fine-grained GPU implementations therefore require atomic updates. Dependency accumulation must likewise combine contributions from multiple successors safely. Sarıyüce et al. avoid explicitly storing predecessor-edge lists and instead identify reverse relationships from the level relation between distances. They also use vertex virtualization, which virtually divides high-degree vertices, to mitigate workload imbalance and atomic contention [@sariyuce2013]. These techniques show that GPU BC performance depends on frontier structure, degree distribution, synchronization frequency, and memory layout, not only on the number of operations.

McLaughlin and Bader present an exact GPU BC implementation that selects work-efficient or edge-parallel traversal according to graph structure. The work-efficient approach uses an explicit vertex frontier to avoid unnecessarily rescanning reached regions. The edge-parallel approach can more readily provide broad parallelism and contiguous memory access. Selection between them is based on frontier evolution and structural information obtained from an initial traversal [@mclaughlin2014]. The same research also appeared as a CACM Research Highlight [@mclaughlin2018]. This chapter uses the 2018 publication page only for bibliographic corroboration. Method details and experimental conditions are based on the fully reviewed 2014 conference paper. This hybridization differs from switching between top-down and bottom-up traversal, discussed below. It addresses the trade-off between work efficiency and GPU utilization in BC.

The study hierarchically combines source-level parallelism, which assigns sources across GPUs, with fine-grained parallelism, which distributes each source's traversal among GPU threads. Its single-GPU evaluation uses a Kepler-generation GTX Titan. Its multi-node evaluation uses Fermi-generation Tesla M2090 GPUs [@mclaughlin2014]. Sarıyüce et al. evaluate a Tesla C2050 and a multi-core CPU [@sariyuce2013]. The target GPUs, CUDA generations, graph sets, normalization conventions, timing scopes, and output definitions differ from those of this study. Their reported performance values are therefore not compared directly with the GH200 measurements in this study.

GPU memory capacity limits source-level parallelism. In a design that concurrently stores distance, $\sigma$, dependency, frontier, and traversal order for multiple sources, storage proportional to batch size times vertex count can dominate. A larger batch can increase parallelism, but it also increases the concurrently resident working set. Conversely, a smaller batch reduces capacity requirements but increases the relative costs of kernel launches, initialization, and synchronization. Graph size alone does not explain this problem.

Taken together, prior results indicate that GPU BC performance is graph-dependent. Wide frontiers can supply fine-grained parallelism but may increase atomic contention. On high-diameter graphs with narrow frontiers, GPU occupancy can decrease and unnecessary scans can have greater impact. Degree skew increases workload differences under vertex-based assignment. Consequently, strong performance by one GPU BC implementation on a particular graph cannot determine its ranking under different implementation conditions and graph structures. This study makes no performance-ranking claim about GPU BC implementations in general.

## 3.3 Direction-Optimizing BFS

Level-synchronous top-down BFS examines outgoing edges from vertices in the current frontier and adds unvisited neighbors to the next frontier. This approach is natural early in a traversal, when the frontier is small, and on high-diameter graphs whose frontiers remain narrow. When the frontier grows in the middle of a traversal, however, many frontier edges can reach the same unvisited vertex. Edges to visited vertices can also be examined repeatedly.

Bottom-up BFS reverses the traversal direction. It considers unvisited vertices and checks whether any neighbor belongs to the current frontier. The search for a vertex can stop after finding one frontier neighbor. It can therefore reduce edge examinations when the frontier is large and the unvisited region is shrinking rapidly. With a small frontier, however, many unvisited vertices may find no frontier neighbor, making the bottom-up scan wasteful.

The direction-optimizing BFS of Beamer et al. switches between top-down and bottom-up traversal at each level. The paper defines $m_f$ as the number of edges leaving the current frontier and treats $m_u$ as an estimate of edges leaving unvisited vertices. It switches to bottom-up when the expected top-down work becomes large and

$$
m_f > \frac{m_u}{\alpha}
$$

holds. The return condition from bottom-up to top-down uses the frontier vertex count $n_f$ and total vertex count $n$: $n_f < n/\beta$ [@beamer2012]. Here, $\alpha$ compares top-down and bottom-up work, while $\beta$ prevents bottom-up traversal from continuing too long after the frontier contracts.

Beamer et al. conduct a parameter study on the graphs evaluated in their paper. Considering average performance and worst-case behavior, they select $\alpha=14$ and choose $\beta=24$ as a value that works well for many graphs [@beamer2012]. The primary paper therefore explicitly reports both values. They are not universally optimal for every graph or hardware platform. They are switching parameters used in the evaluation by Beamer et al. and adopted by the implementation in this study.

The effect of direction optimization depends on graph structure. On low-diameter graphs whose frontiers expand rapidly, bottom-up traversal can reduce unnecessary edge examinations. On high-diameter graphs with small frontiers, switching opportunities are fewer. Converting frontier representations, computing $m_f$, and scanning the unvisited region can then become overhead. Beamer et al. also distinguish the benefit of direction switching from costs such as bitmap and queue conversion [@beamer2012].

Hybrid BFS in this study integrates this established direction-switching concept into source-local BFS for BC. It switches between top-down and bottom-up traversal according to the relationship between the frontier and unvisited region, while retaining each source's shortest-path counts and traversal order. This study does not attribute the origin of Hybrid BFS to itself. Its target is exact all-sources BC, including subsequent dependency accumulation, rather than BFS alone. Component ablation therefore evaluates the effect of switching on the complete BC computation.

## 3.4 PathMerge and GPU Baselines

Galliot is published research intended to reduce auxiliary-memory consumption in GPU-based BC computation through path merging [@zheng2023galliot; @zheng2023jsac]. This study positions Galliot as a memory-oriented direction in GPU BC research that differs from retaining Brandes-based per-source state. The available primary sources did not permit independent verification of the full paper text. This chapter therefore does not supplement the internal path-merging procedure, detailed BFS strategy, implementation specifications, performance values, or implementation-level asymptotic complexity.

The evaluation target called PathMerge in this study is not the code from the Galliot papers but a third-party implementation. Its upstream third-party repository is `gobardhanm/path-merging-bc`, and it has not been confirmed as an official implementation by the original paper's authors [@pathmergeRepo]. Neither fidelity to the papers nor the exact upstream commit identity of the evaluated snapshot has been confirmed. The retained evaluation snapshot is fixed and archived, but this thesis does not assume that its code is fully identical to the published algorithm. The implementation is an external comparator for performance and output comparisons with the proposed implementation. It is not ground truth for determining correct answers.

No explicit license in a LICENSE or COPYING file was confirmed for the evaluated upstream third-party repository [@pathmergeRepo]. This is a provenance constraint on permission to redistribute or modify the code, separate from the validity of the measured performance values. The archived repository material is used under the review and sharing conditions stated for the thesis archive. Detailed handling is deferred to the discussion of reproducibility and limitations.

The performance comparison is limited to the third-party implementation snapshot retained and evaluated in this study, the 4 evaluated graphs, and the GH200 environment. The results are not generalized to the PathMerge algorithm, an implementation by the Galliot authors, another repository, another GPU, or unevaluated graphs. Interpretation keeps several facts separate: the target is a third-party implementation; official status has not been confirmed; and it is an external comparator, not ground truth. Its exact upstream commit identity, fidelity to the papers, and upstream license are also unconfirmed.

cuGraph was adopted as a supplementary baseline because it is a widely used GPU graph-analytics library [@rapidsCugraph]. Its official API distinguishes exact BC over all sources, when no source list is specified, from approximate BC over selected sources [@rapidsCugraphBcDocs]. This study used the exact condition. However, the retained cuGraph comparison is limited to legacy partial data for small graphs. It is not a uniform comparison across all graphs that includes the current block implementation.

The Sequential baseline is the serial Brandes algorithm on a CPU. The OpenMP baseline is a CPU-parallel implementation using source-level parallelism [@brandes2001; @openmp52]. They provide supplementary controls for understanding differences in execution models introduced by GPU computation. As with cuGraph, there is no uniform measurement of the current implementation series across medium and large graphs. Rankings on large graphs are therefore not inferred from the retained Sequential, OpenMP, or cuGraph values. These baselines are not used in the main comparison in Chapter 6.

The baselines have different roles. The third-party PathMerge implementation is the primary external comparator. cuGraph provides a supplementary comparison with a library implementation. Sequential and OpenMP provide supplementary comparisons with CPU execution. None defines the numerical answer in this study as ground truth. Correctness is evaluated separately against an independent CPU reference or through full-vector cross-comparisons.

## 3.5 Unified Memory and Out-of-Core Processing

CUDA Unified Memory (UM) provides a unified address space accessible from the CPU and GPU, together with mechanisms that manage placement and movement. Managed allocation through `cudaMallocManaged` allocates a region accessible from both host and device code [@nvidiaCudaProgrammingGuide; @nvidiaCudaRuntimeApi]. In contrast, pure device memory uses APIs such as `cudaMalloc` to allocate regions in device memory and explicitly manages necessary host-device transfers. The two approaches differ in addressability, placement control, and treatment of capacity constraints.

In an environment with page migration, the runtime can move a nonresident page between host and device memory in response to a page fault from the GPU. `cudaMemPrefetchAsync` is a stream-ordered hint for placing data near a specified processor and can initiate migration according to execution order [@nvidiaCudaProgrammingGuide; @nvidiaCudaRuntimeApi]. Prefetch does not change correctness. It is a performance mechanism intended to reduce page faults when the predicted and actual access patterns agree.

Li et al. report an evaluation of early-generation UM on CUDA applications [@li2015um]. Their study concerns the CUDA 6.x generation and is not treated as research that evaluates later GPU-memory oversubscription. Knap and Czarnul compare standard memory management, basic UM, UM with prefetch, and oversubscription on Pascal and Volta GPUs across several CUDA applications. Prefetch performance depends on the application, stream use, and GPU, and prefetch does not improve performance under every condition [@knap2019um]. Performance improvement therefore cannot be assumed from the presence of prefetch alone.

Oversubscription is the ability to allocate a managed working set larger than the physical memory capacity of one processor and handle needed data between device and host memory [@nvidiaCudaProgrammingGuide]. It relaxes device-memory capacity constraints but does not provide unlimited capacity. Feasibility depends on available host memory, process or system memory limits, page-migration or remote-access costs, and access locality. Frequent movement in both directions can reduce performance even when sufficient capacity is available.

Out-of-core graph processing addresses cases where all graph data cannot remain resident in GPU memory. It supplies required portions to the GPU through graph partitioning, active-subgraph generation, or streaming. Subway generates a SubCSR containing active edges in each iteration for out-of-GPU-memory vertex-centric graph processing, reducing transferred data. It also supports asynchronous subgraph processing for applicable algorithms [@nodehisabet2020subway]. The study further shows that page-fault overhead and page-granularity transfers under UM can limit performance depending on the application and graph.

Shirahata et al. also provide an existing example of out-of-core GPU memory management for MapReduce-based large-scale graph processing [@shirahata2014outofcore]. The full primary text was not independently available. This chapter therefore does not describe its partitioning policy, streaming granularity, or performance characteristics beyond the scope supported by its title and audited metadata.

Chunked in this study is not the same as graph partitioning or active-subgraph streaming. Chunked divides the concurrently processed source set, not the input graph. It divides an outer batch into source sub-batches and uses the entire input graph for each sub-batch. Because every source is eventually processed, it preserves exact all-sources BC and performs no sampling-based approximation.

This distinction also separates graph-file size from the batch-dependent working set. Even if the input graph fits in device memory, concurrently allocating source-local state for many sources can make the working set exceed device memory. In out-of-core processing of a graph that is itself large, placement of the graph topology or active subgraph is the primary concern. Chunked controls the former case through source sub-batching. UM handles the same source-local working set through managed allocation, while Pure places it explicitly in device memory. This study therefore does not position its method as identical to Subway or as out-of-core graph processing itself.

## 3.6 Positioning of This Work

This study targets exact all-sources BC on undirected, unweighted graphs. It groups sources into batches at the outer level. With block-based source assignment, 1 block handles 1 source. Within each source, it integrates Hybrid BFS into source-local BFS and uses Warp-Cooperative Accumulation for dependency accumulation. Dual-Stream Execution further seeks to overlap initialization and computation. Together, these established features form an integrated GPU execution framework for BC [@beamer2012; @nvidiaCudaProgrammingGuide].

The memory approaches are treated as variants of this common framework. UM uses managed allocation and runtime migration mechanisms. Pure uses pure device memory and explicit transfers. Chunked divides source batches into sub-batches and limits the concurrently resident source-local working set. UM, Pure, and Chunked are therefore not three independent proposals. Chunked is source sub-batching for exact BC over the entire input graph, not graph partitioning.

The novelty of this study does not lie in originating the Brandes algorithm, Hybrid BFS, CUDA streams, Unified Memory, or individual warp primitives. Its central position is the integration of these components into a batch-based, block-based BC execution framework that makes UM, Pure, and Chunked comparable within one implementation family. The evaluation also connects end-to-end performance, component ablation, memory scalability, and full-vector numerical validation within the same design family.
